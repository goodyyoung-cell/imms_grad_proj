### 2026-11-26: 관리 화면용 로그인과 조회 API
- 결정: 브라우저 화면은 `POST /auth/login`(이름 + 팀 공유 비밀번호 `ADMIN_PASSWORD`)으로 8시간짜리 서명 토큰을 받아 `/admin/*`을 부른다. 예약 실행·CLI·외부 서버는 계속 `JOB_TOKEN`.
  - 이유: `JOB_TOKEN`은 승인·발송까지 할 수 있는 서버 공용 토큰이라 공개 저장소의 화면 코드에 넣을 수 없다. 로그인 이름은 승인·통화 기록의 '누가'로 자동 기록된다.
  - 토큰은 서버에 저장하지 않고 HMAC 서명만 한다 (서명 키 `ADMIN_TOKEN_SECRET`, 없으면 `JOB_TOKEN`에서 파생). 로그인은 IP당 분당 5회.
- CORS: `ALLOWED_ORIGINS`(기본: localhost 개발 포트들). 화면을 다른 주소에 올리면 추가한다.
- 화면용 조회 API 추가: `/admin/summary`, `/admin/leads`, `/admin/leads/{id}`, `/admin/runs`, `/admin/runs/{id}`. 메일·전화 목록에 리드 요약과 바로 읽을 콜 스크립트 텍스트 포함.
- 프론트엔드는 `web/` 폴더, 안내는 [`frontend-handoff.md`](frontend-handoff.md).
- 검토한 대안: 사용자별 계정(시연용으로는 과함), 같은 서버에서 화면을 띄우고 쿠키 세션(팀원의 프레임워크 선택을 제한)
- 상태: 확정

### 2026-11-26: 첫 실제 LLM 평가 (답장 분류 24건)
- 결과: Claude(`claude-sonnet-5-5`)와 Gemini(`gemini-3.8-flash`) 모두 정확도 95.8% (24건 중 23건). 근거 있는 질문 4건에만 답변 초안을 만들고, 근거 없는 질문(ISMS 인증)은 둘 다 사람에게 넘겼다.
- 둘 다 틀린 사례는 R23 "지금 쓰는 헬프데스크가 있어서요. 굳이 바꿀 필요는 못 느낍니다." (정답: not_now)
  - Claude: unclear(확신도 0.5) → 사람에게 이관. 안전한 오답.
  - Gemini: unsubscribe(확신도 0.75) → **연락 전면 중단**. 규칙상 LLM이 수신 거부로 분류하면 확신도와 관계없이 멈추기 때문. 잠재 고객을 잃는 오답.
- 결정 (같은 날): 규칙이 감지하지 못하고 **LLM만 수신 거부로 본 경우, 확신도 0.9 이상이면 즉시 중단, 미만이면 담당자가 확인**한다.
  - 확인 전까지는 수신 거부가 처리되지 않으므로, 대기 중인 전화 과제에 "수신 거부 의심, 확인 전 통화 보류" 알림을 붙인다 (메일은 원래 사람 승인 없이 나가지 않음).
  - 담당자는 `cli unsubscribe <lead_id> --by 이름` 또는 `POST /admin/leads/{id}/unsubscribe`로 확정한다. 확정하면 남은 메일·전화를 DB 트리거가 취소한다.
  - 규칙(수신 거부 표현)이 감지한 경우는 지금처럼 LLM 없이 즉시 중단한다.
  - 이 기준이면 위 R23 Gemini 사례(0.75)는 담당자 확인으로 넘어간다.
- 검토한 대안: 지금처럼 즉시 중단 / 즉시 중단 후 확인 알림

### 2026-11-26: 첫 메일 발송 1시간 뒤 전화 팔로업과 콜 스크립트
- 결정: 첫 메일이 승인·발송되면 **발송 1시간 뒤**(평일 9~18시 밖이면 다음 평일 9시) 전화 팔로업 과제와 콜 스크립트를 자동으로 만든다.
  - 목적: ① 메일 수신 확인 ② 미팅 희망 시기 ③ 고객사의 **Compelling Reason**(왜 지금 바꿔야 하는가: 계기·영향·미해결 비용·기한·반길 사람) 찾기.
  - 스크립트는 에이전트가 쓴다 (내부 준비 자료라 자율). 근거 규칙은 메일 초안과 같고, 통화 허락·녹음 동의·연락 거부 시 종료 문구는 코드가 넣는다. 키가 없으면 기본 스크립트.
  - **전화는 SDR이 직접 건다.** 인터넷·유선 전화와 연동하지 않는다. 콜 과제는 SDR의 할 일 목록이다.
  - **시스템이 콜 과제를 취소하는 경우는 수신 거부 하나뿐**(DB 트리거). 답장이 오거나 인계되면 취소하지 않고, 통화 전에 볼 수 있게 과제에 알림을 붙인다.
  - SDR은 통화 결과와 함께 메일 수신 여부, 희망 미팅 시기, Compelling Reason을 기록한다. 관심이면 인계되고, 인계 요약에 이 내용이 들어간다. 이미 인계된 리드는 통화 결과로 상태를 되돌리지 않는다.
- 이유: 메일만 보내고 전화 팔로업이 없으면 영업기회 전환율이 떨어진다. 메일 직후 짧은 통화가 수신 확인과 관심 확인에 효과적이다.
- 검토한 대안: 다음 영업일 오전 10시 통화 (대체됨), 답장이 오면 콜 과제 자동 취소 (전화 연동이 없어 의미가 없으므로 대체됨)
- DB: `call_tasks` 테이블, 수신 거부 트리거 확장, 통화에서 들은 내용 컬럼 (`20261125010000_call_tasks.sql`, `20261126000000_call_followup_capture.sql`)
- 상태: 확정

### 2026-11-25: 리드 유입 경로 두 가지와 중복 병합 규칙
- 결정: 리드는 두 입구로 들어오고, 같은 정규화·중복 규칙(`sdr_agent/intake.py`)을 거친다.
  1. **웹사이트 폼**: 서버가 직접 띄우는 데모 신청 폼(`GET /form`, `POST /form/submit`, 공개). 외부 폼 서비스는 서버에서 `POST /webhooks/lead`(JOB_TOKEN)로 보낸다.
     개인정보 수집·이용과 AI 활용 고지 동의를 필수로 받고 `leads.consent_at`에 시각을 남긴다. 봇 방지 숨은 칸, IP당 1분 5회 제한.
  2. **직원 시트 업로드**: CSV·엑셀 파일 또는 구글 시트. 열 이름은 한국어·영어 별칭을 인식한다(`sheets.py`). **기본은 미리보기**이고 확인 후 저장한다 (CLI `--commit`, API `dry_run=false`).
     구글 시트는 '링크가 있는 모든 사용자' 공개 대신 Cloud Run 서비스 계정에 보기 권한으로 공유해 읽는다 (개인정보 보호).
- 중복 규칙: ① 같은 이메일 + 같은 유입 유형 → 이미 있음(저장 안 함, 재업로드 대비) ② 같은 이메일 → 같은 사람, 대표 리드에 병합 ③ 같은 회사(도메인 또는 법인 표기를 뺀 회사명) → 같은 회사 다른 담당자, 대표 리드에 병합 ④ 그 외 신규.
  회사당 대표 리드 하나만 에이전트가 처리해 같은 회사에 메일이 몰리지 않게 한다. 병합 수는 점수의 '여러 채널 유입' 가점이 된다.
- 수신 거부한 사람이 다시 들어오면 자동으로 연락을 재개하지 않고 사람에게 알린다.
- 새 리드는 상태 `new`로 들어가고 예약 실행이 조사한다 (유입 즉시 조사는 하지 않음: Cloud Run은 응답 뒤 백그라운드 작업의 CPU를 보장하지 않는다).
- DB 변경: `leads.intake_channel`(web_form·sheet_upload·manual·seed), `leads.consent_at` 추가 (`20261125000000_lead_intake.sql`).
- 상태: 확정

### 2026-11-25: 리서치 출처를 홈페이지·DART·네이버 뉴스·Google 뉴스로 확장
- 결정: 리서치 에이전트가 네 출처 중 무엇을 볼지 스스로 고른다. 홈페이지는 사업·제품·고객, DART는 재무·공시, 뉴스는 최근 소식과 대화 소재.
  - 네이버 뉴스: 공식 검색 API(`NAVER_CLIENT_ID/SECRET`). 키가 없으면 도구가 오류를 돌려주고 에이전트가 Google로 넘어간다.
    - **2026-11-26 갱신**: 검색 API 신청이 2026년 여름부터 네이버 클라우드 플랫폼 **NAVER API HUB**로 옮겨졌다. 주소 `naverapihub.apigw.ntruss.com/search/v1/news`, 헤더 `X-NCP-APIGW-API-KEY-ID/KEY`. 응답 형식은 같다. 예전 개발자센터 키는 쓸 수 없어 새로 발급한다. 예전 방식은 `NAVER_SEARCH_API=legacy`로 남겨 둔다. 한시적 무료, 일 25,000회 (https://api.ncloud-docs.com/docs/naver-api-hub-search-news).
  - Google 뉴스: 공개 RSS, 키 불필요. 최근 1년 기사만.
  - 기사는 제목·요약만 받는다. 검색 결과로 받은 기사 url만 출처로 인정한다 (기존 출처 규칙 그대로).
  - 홈페이지: 리드 도메인으로 https → www 순으로 시도. 자바스크립트·meta refresh로 넘기는 첫 화면은 한 번 따라가고, 오래된 TLS 사이트는 보안 수준을 낮춰 다시 읽는다(공개 페이지 읽기 전용).
  - **봇 차단(403 등)은 우회하지 않는다.** 다른 출처를 쓰라고 에이전트에게 알린다. 샘플 10개 회사 중 쿠팡이 차단, 대한항공은 자바스크립트로만 그려져 본문이 비어 있다.
  - 출처가 늘어 `AGENT_MAX_STEPS` 기본값을 8 → 12로 올렸다.
- 이유: DART만으로는 비상장사와 최근 소식을 채울 수 없고, 첫 메일의 대화 소재는 뉴스에서 가장 많이 나온다. scope.md의 "일정이 밀리면 뉴스를 뺀다"(대체안 1번)는 적용하지 않는다.
- 상태: 확정

  - LLM: **Claude와 Gemini**를 함께 쓴다. 공통 어댑터 하나로 감싸 모델을 바꿔 끼울 수 있게 한다. 기본 배치는 에이전트 루프는 Claude, 대량 요약·비교 실험은 Gemini로 시작한다.
  - 실행: **Google Cloud Run** (웹훅용 서비스 + 예약 실행, Cloud Scheduler). 필수. 개발은 로컬에서 하고, 뼈대부터 배포해 두고 기능을 얹는다
  - DB: **Supabase** (Postgres). 리드 상태, 실행 로그, 승인 기록을 저장한다. RAG용 벡터 저장은 Supabase pgvector를 우선 검토한다.
- 이유:
  - Python은 RAG·평가 분석 생태계가 가장 두껍고, Claude·Gemini SDK와 Google API, Cloud Run 모두 잘 지원한다.
  - 에이전트 루프는 리드 10건 기준 수 분이 걸린다. Cloud Run은 요청 제한을 최대 60분까지 늘릴 수 있고, 작업은 더 길게 돌릴 수 있다.
  - Supabase Edge Functions만으로는 실행 시간(무료 150초, 유료 400초)과 요청당 CPU 2초 제한이 에이전트 루프에 빡빡하다.
- 검토한 대안: TypeScript(기존 프로토타입이 JS), Streamlit 단일 앱, Chrome 확장, Supabase 단독
- 미정: 벡터 DB 최종 선택, 이메일 샌드박스 서비스, 승인 채널(Slack 또는 이메일)
- 상태: 확정 (미정 항목 제외)

### 2026-11-21: 서비스 형태는 에이전트형 백엔드
- 결정: 사람이 화면을 열어야 시작하는 도구(Chrome 확장, 대시보드)가 아니라, **서버에서 스스로 도는 에이전트**로 만든다.
  - 시작: 새 리드 유입, 정해진 시간, 승인 클릭, 답장 도착 같은 이벤트가 에이전트를 깨운다.
  - 판단: LLM이 목표와 도구 목록을 받아 다음 행동을 고르고, 결과를 보고 다시 시도한다.
  - 경계: **내부 작업(리서치, 점수, 초안)은 자율, 고객에게 나가는 행동(발송, 후속)은 사람 승인.**
  - 접점: 승인 요청과 보고는 메일·메신저로 보낸다. 웹은 설정과 실행 로그를 보는 관리 화면 정도로 둔다.
- 이유: 고정된 순서로 LLM을 부르는 도구는 워크플로우일 뿐 에이전트가 아니다. 동시에 수업 팀과제(Team 13)에서 진행한 SDR·BDR 실무자 인터뷰 3건에서 모두 할루시네이션과 책임 소재를 우려했고 고객에게 나가는 메시지는 사람이 확인하길 원했으므로, 자율성은 내부 작업에만 준다.
- 검토한 대안: Chrome 확장 + 사이드패널, Streamlit 대시보드
- 상태: 확정
