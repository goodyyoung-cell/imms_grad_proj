# 소식 기반 초안, 대화형 에이전트, 피드백 메모리: 변경 내용 정리

2026-11-28에 추가한 세 가지 기능의 동작, 안전장치, 데이터와 API 변경, 검증 상태를 한곳에 모았다.
발표자료와 보고서를 고칠 때 아래 "문서에서 고칠 곳"을 기준으로 삼는다. 화면이 쓰는 API 계약은 [`chat-memory-api.md`](chat-memory-api.md)에 있다.

## 1. 한눈에

| 기능 | 하는 일 | 사람이 보는 곳 |
|------|---------|----------------|
| 소식 기반 초안 | 회사 소식, 없으면 업종 화두로 메일 오프닝을 열고, 제목 후보 3개를 함께 만든다 | 승인 화면, Slack 승인 카드 |
| 대화형 에이전트 | 말로 초안을 다시 쓰게 하고, 제목을 고르고, 승인·반려·발송을 지시하고, 피드백을 남긴다 | 관리 웹 우측 상단 "AI 에이전트" 패널, Slack(DM, 멘션, 승인 카드 스레드) |
| 피드백 메모리 | 남긴 지침을 한 줄 규칙으로 저장하고, 다음 메일·답장·통화 스크립트를 만들 때 자동 반영한다 | 메모리 화면, 초안의 "반영된 피드백" |

기존 원칙은 그대로다. 리서치·점수·초안은 자율이고, 고객에게 나가는 행동은 사람의 승인(또는 사람의 직접 지시)이 있어야 한다.

## 2. 소식 기반 초안

**어떤 소재를 쓰는가.** 초안 에이전트가 소재(hook)를 다음 순서로 고른다.

1. 회사 소식: 리서치에서 이미 모은 `recent_news`, `talking_point` 사실. 오늘 기준 약 30일 이내이고 고객 문의 응대와 이어지는 것.
2. 업종 화두: 회사 소식이 마땅치 않을 때. 업종별 최근 기사 중 21일 이내인 것.
3. 문의 사유: 둘 다 없을 때 (데모 요청 등 유입 경로).

유출·사고·소송·구조조정 같은 민감한 소식은 소재로 쓰지 않는다 (사실 카드에 `sensitive`로 표시하고, 제출 단계에서 코드가 거부한다). 소재 문장은 근거 사실(`fact_id`) 또는 업종 기사를 인용해야 하고, 근거 규칙은 기존 초안과 같다.

**업종 브리프.** 회사 소개·제품·업종 사실과 회사명의 키워드로 13개 업종 중 하나를 정하고(못 정하면 업종 소재를 쓰지 않는다), 업종별 최근 기사를 네이버·Google 뉴스에서 모아 `industry_briefs`에 7일 동안 재사용한다. 리드마다 검색하지 않는다.

**제목은 세 가지.** 모두 45자 이내이고 (프롬프트는 40자), 승인자가 고른다.

| 후보 | 내용 | 기본 |
|------|------|------|
| 일반 제목 (`general`) | 회사명과 소재 없이 가치 중심 | 기본값 |
| 회사명 포함 (`company`) | 회사명이 들어간 제목 (코드가 회사명 포함 여부를 검사) | |
| 소식 반영 (`hook`) | 오프닝 소재를 반영한 제목. 소재가 문의 사유이면 만들지 않는다 | |

**오픈률은 측정하지 않는다.** 이 기능은 기능 구현까지만 범위로 한다 (샌드박스 발송이라 수신자가 없다).

## 3. 대화형 에이전트

**부르는 법**

| 경로 | 방법 |
|------|------|
| 관리 웹 | 우측 상단 "AI 에이전트" 버튼 → 우측 패널. 지금 보는 메일·고객을 자동으로 맥락에 넣는다 |
| Slack DM | 앱 메시지 탭에서 바로 말한다 |
| Slack 채널 | `@SDR Agent ...`. 이어지는 스레드 말은 같은 대화 |
| Slack 승인 카드 | 카드의 스레드에 답글. 그 카드의 메일이 "이 메일"이 된다 |

**도구**: 승인 대기·리드 조회, 현황, 초안 다시 쓰기(전체·제목만·본문만), 문구 직접 수정, 제목 후보 선택, 발송(승인), 반려, 피드백 저장·조회·삭제. 다시 쓰기 전 버전은 `revisions`에 남고, 승인 카드는 같은 내용으로 갱신된다.

**안전 규칙 (모두 코드로 막는다)**

- 발송·반려·피드백 삭제는 사용자가 **그 메시지에서 직접 지시한 경우에만** 실행한다. 지시가 분명하면 확인 카드 없이 바로 실행한다. 질문("보내도 될까?"), 부정("보내지 마"), "전에"가 든 말은 지시로 보지 않는다. 에이전트가 스스로 판단해 발송하는 길은 없다 (도구가 거부한다).
- 발송은 버튼 승인과 같은 `decide_message()`를 탄다. AI 사용 고지, 수신 거부 안내, 전송자 정보, 수신 거부 차단, 하루 발송 상한이 그대로 적용된다. 승인 기록의 채널은 `chat_web`, `chat_slack`이다.
- 이번 대화에서 조회했거나 화면·카드가 알려 준 메일만 다룰 수 있다 (모르는 id를 만들어 발송할 수 없다). 한 번에 발송·반려는 5건까지.
- 고객 답장, 기사, 리서치 사실 안의 문장은 데이터일 뿐이다. 도구 결과에 든 지시는 따르지 않는다.
- Slack은 `SLACK_APPROVERS`에 든 사용자만 쓸 수 있게 한다 (비어 있으면 봇이 있는 곳의 모든 사용자).

## 4. 피드백 메모리

- **무엇을 저장하나**: 사용자가 앞으로도 적용하라고 한 지침을 한 줄 규칙(300자 이내)으로. 예: "제목은 30자 안으로 쓴다". 일회성 수정 요청은 저장하지 않는다.
- **범위**: 고객 > 업종 > 전체. 좁은 범위가 우선하고, 충돌하면 좁은 쪽을 쓴다. 한 번에 최대 8건(고객 4, 업종 3, 전체 4)을 프롬프트에 넣는다.
- **언제 반영하나**: 첫 메일 초안, 답장 응대(질문에 대한 답변 초안), 통화 스크립트를 만들 때. 다시 쓰기에도 반영한다.
- **추적**: 초안·답변·스크립트가 쓴 규칙의 id가 결과물의 근거 목록(`citations`, type=`feedback`)에 남고, 화면에 "반영된 피드백 n건"으로 보인다. 규칙마다 반영 횟수(`applied_count`)를 센다.
- **관리**: 메모리 화면에서 조회, 추가, 수정, 보관, 삭제. 챗으로 저장하면 어느 범위에 저장했는지 답변에 밝힌다.
- **저장하지 않는 것**: 이메일 주소·전화번호 같은 개인 연락처, AI 사용 고지·수신 거부 안내·전송자 정보를 바꾸는 지침 (코드가 거부). 근거 규칙과 안전 규칙은 피드백보다 우선한다고 프롬프트에도 명시한다.
- **개선 방식**: 파인튜닝이 아니라 저장된 규칙을 프롬프트에 넣는 방식이다. 기존 "파인튜닝은 후속 과제, 이번 학기는 프롬프트와 RAG" 결정과 같은 선상에 있다.
- **이번에 하지 않는 것**: 무응답 시 후속 메일 신설 (결정 유지), 승인 시 수정 diff에서 규칙 자동 추출.

## 5. 데이터와 API 변경

**마이그레이션** `supabase/migrations/20261128000000_chat_memory.sql` (여러 번 실행해도 안전)

| 대상 | 변경 |
|------|------|
| `messages` | `subject_options`, `subject_choice`, `hook`, `revisions`, `slack_ref` 열 추가 |
| `industry_briefs` | 신규. 업종 키별 기사 목록과 수집 시각 |
| `feedback_notes` | 신규. 범위, 종류, 한 줄 규칙, 출처, 상태, 반영 횟수 |
| `chat_sessions`, `chat_turns` | 신규. 대화 세션과 발화 (Slack 이벤트 id로 중복 처리 방지) |

**엔드포인트**

| 메서드 경로 | 설명 |
|-------------|------|
| `POST /admin/messages/{id}/subject` | 제목 후보 선택 |
| `GET /admin/feedback`, `POST`, `PATCH /{id}`, `DELETE /{id}` | 메모리 관리 |
| `GET /admin/industries` | 업종 목록 |
| `POST /admin/chat`, `GET /admin/chat/sessions/{id}` | 관리 웹 챗 |
| `POST /webhooks/slack/events` | Slack 이벤트 (서명 검증, 즉시 응답 후 백그라운드 처리) |
| `GET /admin/messages`, `/admin/leads/{id}` | 응답에 제목 후보, 소재, 이전 버전, 반영된 피드백 추가 |
| `GET /admin/status` | `chat`, `memory` 항목 추가 |

**Slack 앱**: 권한(`app_mentions:read`, `im:history`, `im:write`, `channels:history`, `users:read`)과 이벤트 구독(`app_mention`, `message.im`, `message.channels`) 추가, 재설치 필요. 설정 방법은 [`admin-slack.md`](admin-slack.md) 6.1절. Cloud Run은 `--no-cpu-throttling`이 필요하다.

## 6. 구현 상태와 검증

- 백엔드 테스트 233건 통과 (이번 기능 51건 추가). 가짜 LLM·가짜 DB로 소재·제목 규칙, 민감 소식 거부, 피드백 반영과 추적, 챗의 직접 지시 판별과 발송 차단, Slack 이벤트 걸러내기와 서명 검증, 관리 API를 검증한다.
- 실제 LLM(Claude)으로 5개 리드의 초안을 만들어 보았다: 근거 오류 0건, 4곳은 회사 소식, 1곳은 문의 사유로 소재를 골랐고, 챗의 "대기 중인 승인 요청 보여줘"가 5건을 정확히 나열했다. 이 점검에서 일반 제목이 5곳 모두 같은 문장으로 나오는 문제를 발견해, 프롬프트에서 예시 문장을 빼고 리드마다 다르게 쓰도록 고쳤다.
- 다시 쓰기, 피드백 저장, 발송 지시를 실제 LLM으로 끝까지 돌려 보는 점검은 Anthropic API 크레딧 소진으로 끝내지 못했다 (Gemini 응답도 지연). 이 흐름은 가짜 LLM 테스트로만 검증됐다. 크레딧 충전 후 `scripts/eval_chat_memory.py`로 다시 돌린다.

## 7. 문서에서 고칠 곳 (발표자료·보고서)

| 위치 | 고칠 내용 |
|------|-----------|
| 기능 범위·모듈 소개 | 모듈 2(이메일 소통)에 "소식 기반 소재와 제목 후보"를, 새 요소로 "대화형 에이전트"와 "피드백 메모리"를 추가 |
| 시스템 구조도 | 업종 브리프(뉴스 수집), 챗 진입점(관리 웹 패널, Slack), 피드백 메모리 저장소와 초안 생성으로의 주입 화살표 추가 |
| 자율과 승인의 경계 | "고객에게 나가는 행동은 사람 승인"에 "사람의 직접 지시(챗)로도 발송 가능, 에이전트의 자율 발송은 코드로 차단"을 보탠다 |
| 안전·컴플라이언스 | 챗 발송도 같은 승인 경로(법정 고지, 수신 거부 차단, 발송 상한)를 탄다는 점, 법정 고지는 피드백으로 못 바꾼다는 점 |
| 개인화·고도화 | 소재 선정 우선순위(회사 소식, 업종, 문의 사유), 민감 소식 제외, 제목 3종과 기본은 일반 제목 |
| 지속 개선 | 피드백이 고객·업종·전체 범위로 저장되어 다음 접점에 반영되는 흐름. 파인튜닝이 아니라 프롬프트 주입 방식임을 명시 |
| 범위 제외·한계 | 무응답 후속 메일은 여전히 제외, 오픈률 측정 안 함, 피드백 자동 추출(승인 수정 diff)은 후속 과제 |
| 화면 캡처 | `SDR관리화면_스크린샷\` 21~26번 (제목 후보와 소재, AI 에이전트 패널 A·B, 메모리 화면, 챗 액션 칩, 고객 상세 피드백) |
| 평가 | 오픈률 지표는 없음. 소재 적용률, 근거 일치율, 승인 수정률 같은 기존 지표를 그대로 쓴다 |
