# AI SDR 시장·규정 조사와 우리 빌드에 반영한 것

조사일 2026-11-26. 제품 문서와 법령 원문을 직접 읽은 것만 **확인**으로 적고, 읽지 못한 것은 **미확인**으로 구분했다.
이 조사에는 웹 검색 도구가 없어 페이지를 직접 열어 읽는 방식이었고, 일부 제품(Salesforce 도움말, Reply.io, Salesloft, Lemlist 등)은 열리지 않았다.

## 2. Slack 알림은 제품들이 어떻게 쓰나

- 일반 이벤트(새 답장, 수신 거부, 미팅 예약, 부재, 캠페인 종료, 계정 오류)는 대부분 **단방향 알림**이고, **승인 요청만 버튼으로 실행**한다 (Instantly, Apollo). 11x는 계정별 스레드와 담당자 자동 멘션, Apollo·Common Room은 일일 요약을 둔다. 근무시간 제한(quiet hours)은 문서에서 찾지 못했다.
- Slack 플랫폼 규칙(docs.slack.dev, 확인): 버튼 응답은 3초 안에 200으로 받아야 하고, `response_url`은 30분·5회, `trigger_id`는 3초 안에 한 번만 쓴다. 메시지는 50블록, section 3000자, header 150자, 버튼 25개까지. 메시지 작성은 채널당 초당 1건 정도이고 429 응답의 `Retry-After`를 따른다. url 버튼도 클릭 이벤트가 오므로 200으로 받아 줘야 한다.

**우리 구현에서 이 조사로 고친 것**
- 모달이 닫힌 뒤 `response_url`이 만료돼도 `chat.update`로 메시지를 바꾼다 (채널·ts를 모달에 담음).
- 429를 받으면 `Retry-After`만큼 기다렸다가 한 번 더 보낸다.
- url 버튼 클릭을 조용히 받아 준다 (이미 처리).
- 승인 대기가 오래되면 알린다 (`POST /jobs/remind`, Cloud Scheduler).
- 반려는 사유를 고르는 창을 거친다. 반려 사유는 평가와 프롬프트 개선 자료가 된다.

**남은 위험**: 결정을 요청 안에서 동기로 처리하므로 콜드 스타트가 길면 3초를 넘겨 버튼이 오류로 보일 수 있다 (처리는 끝나고 결과는 메시지에 반영된다). `--min-instances 1`을 권한다. Slack이 인터랙션을 재시도하는지는 문서에서 확인하지 못해, 처리는 멱등하게 만들었다 (이미 처리된 메시지는 "처리하지 못했습니다"로 안내).

## 3. 한국 규정 (법제처 국가법령정보센터 원문을 읽음)

**이전 자료의 모순을 풀었다**: 정보통신망법 제50조 제3항의 야간(오후 9시~오전 8시) 별도 동의는 "대통령령으로 정하는 매체" 예외가 있고, 시행령 제61조 제2항이 그 매체를 **전자우편**으로 정한다. 따라서 **이메일에는 야간 별도 동의가 필요 없다** (문자·카카오·전화에는 필요). 이전 문서의 "야간 별도 동의가 적용된다"는 문장은 이메일에는 틀렸다. 다만 사전 동의(제1항)·수신 거부(제2항)·표시(제4항)는 이메일에도 그대로 적용된다.

| 규정 | 내용 | 우리 구현 |
|------|------|-----------|
| 제50조 제1항 | 영리목적 광고성 정보는 수신자의 명시적 사전 동의가 필요. 예외는 직접 수집한 거래 관계 6개월 이내와 전화 권유뿐. **B2B 예외 없음** | 웹 폼 동의는 `consent_at`에 기록. 직원 업로드 리드는 동의 없음 → **`REQUIRE_CONSENT_TO_SEND`로 동의 없는 리드 발송 차단**(실발송 때 켠다), 담당자가 동의 근거를 남기는 화면 추가 |
| 제50조 제2항 | 수신 거부·철회 후 전송 금지 | 답장 감지 + DB 트리거 + 메일 하단 링크로 즉시 중단 |
| 제50조 제4항, 시행령 제61조 별표 6 | 전송자 명칭·연락처, 수신 거부 방법 표시. 제목 맨 앞 "(광고)", 안내는 한글·영문, 로그인 없이 한 번에 (별표 6 원문은 못 읽고 협회 해설서로 확인) | **제목 "(광고)" 접두, 영문 수신 거부, 전송자 정보, 한 번에 처리하는 수신 거부 링크** 추가 |
| 제50조 제5항 | 수신 거부 회피·방해, 주소 자동 생성·**자동 등록** 금지 (형사처벌) | 스크래핑으로 연락처를 모으는 기능을 만들지 않는다 |
| 제50조 제7항, 시행령 제62조의2 | 거부·철회 처리 결과를 14일 이내 알림 | 수신 거부 링크 화면이 처리 결과를 즉시 보여 준다. 답장으로 거부한 경우의 별도 안내는 미구현 |
| 제50조 제8항, 시행령 제62조의3 | 동의받은 사람에게 2년마다 재확인 | 미구현 (기간이 지나기 전에 설계) |
| 개인정보 보호법 제20조 | 정보주체 외에서 수집한 개인정보는 요구 시 출처 고지 | 업로드 출처 기록은 미구현 |
| 인공지능기본법 제31조 | 생성형 AI 기반 서비스는 사전 고지, 결과물 표시 | 모든 메일에 AI 사용 고지를 코드가 붙임 |

제재: 제50조 제1~3항 위반은 3천만 원 이하 과태료(제76조), 제5항 금지행위는 1년 이하 징역 또는 1천만 원 이하 벌금(제74조). 이 문서는 법률 자문이 아니다.

## 4. 이 조사로 정한 개발 범위

만든 것 (이번 브랜치)
1. 승인 화면: 반려 사유, 수정 전 초안 보존, 사람이 검토한 시간 기록, 발송하지 못한 승인 메일 재발송, 수신 동의 경고
2. 평가 지표 화면과 CSV: 승인까지 대기·사람 검토 시간·수정한 정도·반려 사유·답장 분류·실행 성공률, **수작업 기준 시간 기록과 비교**
3. 광고성 메일 표시와 수신 거부 링크, 동의 게이트, 하루 발송 상한
4. Slack: 반려 사유 창, response_url 만료 대비, 429 재시도, 승인 대기 알림

만들지 않은 것과 이유
- 이메일 일괄 승인: 확인된 제품이 없고 "한 건씩 사람이 승인"이라는 신뢰 모델과 충돌한다.
- 대기 만료 시 자동 발송: 어느 제품도 문서화하지 않았고 위험하다. 대기가 길어지면 알리기만 한다.
- 재생성: HubSpot에서만 확인했다. 실제 LLM 키가 없어 검증하기 어려워 미뤘다.
- 리드 오너 멘션·스레드: 리드 담당자와 Slack 사용자를 잇는 정보가 아직 없다.
